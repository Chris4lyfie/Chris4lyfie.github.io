Project Argus — Multi-Sensor Ethernet Monitor

Embedded Systems
May 2026 – Present
C++ / PlatformIO

An ESP32-based sensor node that monitors temperature and humidity across a homelab server closet, delivering live readings to a web dashboard over Ethernet.

Prototype v0.2 — Live & Running
Why I Built This
Wanted to go deeper in embedded
  • I learned a lot from my classes, but I wanted to build something of my own. Building this bridged the gap between theory and real life solutions.
A real problem in my homelab
  • My server closet has a TrueNAS box, a UPS, a Pi stack, and a Xeon server. I had no idea what the temps or humidity were in there. That bothered me.
Build it, don't buy it
  • I could buy something to solve my problems, but where's the fun in that? Building this from the ground up means I understand every aspect of it, hardware, software and networking!
Hardware meets the homelab
  • I wanted it to be part of the infrastructure, not just a plug and play gadget meant to be forgotten.

System Architecture

I designed it to be simple and straightforward. One controller, a handful of sensors, and a way to visually see all the data. Every component was researched and selected before even placing an order.

MCU
  • ESP32-WROOM-32D
  • Runs PlatformIO / Arduino framework
  • Handles HTTP server, sensor polling, and JSON output
  • Serial at 460,800 baud for debugging
Sensors
  • SHT31-D — ambient humidity & temperature (I2C)
  • 5× DS18B20 — point temperature probes (1-Wire)
  • 4.7 kΩ pull-up on GPIO 27 for 1-Wire bus
  • I2C on GPIO 21/22
Networking
  • W5500 Ethernet module (SPI)
  • VSPI pins: GPIO 18, 19, 23, 5
  • Interrupt on GPIO 16
  • Static IP on management VLAN
Power
  • 12V input via buck converter module
  • Regulated to 3.3V for ESP32 and sensors
  • Chosen as a learning exercise — class topic at the time
  • Future: build own buck converter from discrete components
The Circuit

I designed the circuit myself. All of the components, the power delivery, the pin assignments, were thoroughly researched. Different iterations of the block diagram were drawn, mainly because I was indecisive on parts. Despite all of this research, I used AI extensively for sanity checks.

Research alone took 3–4 months of intermittent work, mostly spent deciding whether the project was worth committing to. Once the decision was made, the circuit came together in about two hours. One large mistake was installing the ESP32 upside down — I didn't notice it until I was trying to flash the board and kept getting errors.

Sensor Placement Plan

The five DS18B20 probes share a single 1-Wire bus. Each probe has a unique ROM address, so the firmware reads them independently. The placement plan puts a probe at each major heat-generating component in the closet with one spare for future expansion.

Sensor Type Placement What It's Watching
SHT31-D Temp + Humidity Ambient — closet interior Overall closet environment — the first thing to warn of a ventilation problem
DS18B20 #1 Temperature Inside TrueNAS enclosure Primary storage host — the most thermally critical device in the closet
DS18B20 #2 Temperature Next to UPS UPS battery health is temperature-sensitive — elevated temps degrade capacity over time
DS18B20 #3 Temperature Inside Pi stack Raspberry Pi cluster — runs Pi-hole and Nginx; small form factor means heat can build up
DS18B20 #4 Temperature Inside Xeon server Currently offline — will monitor on power-up to catch thermal issues before they become failures
DS18B20 #5 Spare TBD Reserved for future expansion — possible placement near the core switch or core switch uplink
Build Process

I built the circuit in stages because I wanted to get each subsystem working before introducing a new factor. I started with the humidity sensor, followed by the temperature sensors, and lastly the Ethernet connection.

Web Dashboard

The dashboard is served directly from the ESP32 at a static IP on the management VLAN. Two routes: / returns the full HTML dashboard, and /data returns a JSON payload of current readings. The JSON endpoint means any other service on the network can consume the data without scraping HTML.

The frontend was completely vibecoded. I gave artistic direction (albeit simple), but I had 0 experience with UI design. This project was to show hardware and embedded systems, frontend wasn't my main focus. The final result is functional and clean!

Firmware

This was my first real firmware project. I used references and other people's code extensively — reading through their implementations taught me more about these protocols than any class could. The code is built on PlatformIO with the Arduino framework, with a timer-based non-blocking sensor polling so the HTTP server stays responsive between reads.

The biggest firmware obstacle was the Ethernet server itself. I spent two hours trying to get the standard Ethernet library to initialize correctly, only to be met with an error each time. I tried different libraries, older framework versions in the platformio.ini, different initializations — nothing worked. Eventually I used AI to write a custom EthernetServer wrapper class that fixed all of my problems. It also helped me with chunking the HTTP transmission as a workaround for the hardware buffer constraints.

Known Challenges

These are documented openly because they're the honest state of the prototype. Each one has a known cause and a planned path forward.

Challenge 1 — Cold-Boot Instability
SymptomSystem fails to initialize correctly on some cold boots, requiring a manual reset
Suspected CauseWatchdog timer firing during Ethernet or sensor initialization before the peripherals are ready
Current StateWorkaround: manual reset resolves it. Not acceptable for an always-on monitoring node.
The fix will likely involve adding initialization delays, checking peripheral ready states before proceeding, or configuring the watchdog timeout to accommodate slower startup paths.
Challenge 2 — No Ethernet Reconnection Logic
SymptomIf the Ethernet link drops (switch reboot, cable pull), the system does not attempt to reconnect
CauseNo link-loss detection or reconnection handler implemented in firmware
Current StateRequires a manual power cycle to restore network connectivity after a link event
For a monitoring node intended to run indefinitely, this is a gap. Reconnection logic needs to poll link state and re-initialize the W5500 on loss detection.
Challenge 3 — Breadboard-Only Deployment
SymptomCircuit is on a breadboard with no enclosure, no strain relief, and no permanent mounting
CauseBreadboard was the right choice for a prototype — permanent deployment requires PCB or perfboard
Current StateRunning live but not closet-mounted. Sensors not yet placed at their final locations.
PCB migration is the next major milestone. KiCad is the planned tool — I haven't used it before, so this doubles as a learning exercise.
Challenge 4 — Power Rail Conflicts Under Load
SymptomSimultaneous activation of multiple peripherals causes instability — power distribution not fully validated under load
CauseProtective capacitors not yet installed; power distribution designed but not load-tested
Current StateStable during normal operation; edge cases under full sensor + Ethernet load not fully characterized
Decoupling capacitors on the 3.3V rail are a planned addition before any permanent PCB layout is committed to.
What's Next
01
PCB Design in KiCad

Migrate from breadboard to a proper PCB. I haven't used KiCad before — this is the next learning milestone. A permanent board means proper power traces, decoupling caps, and a form factor that can actually live in the closet.

02
Spike Alerting

When a sensor exceeds a threshold, something should happen — a notification, an alert, something. The dashboard shows color-coded warnings but there's no push notification when I'm away from the page. Email or webhook alerting is the target.

03
Data Logging

Right now the dashboard only shows live readings — there's no history. Logging to a time-series store (likely on TrueNAS) would let me look back at temperature trends over time and spot gradual thermal changes before they become problems.

04
Ethernet Reconnection Logic

Link-loss detection and automatic reconnection in firmware. A monitoring node that goes dark when the switch reboots is not a reliable monitoring node.

05
Build a Custom Buck Converter

Currently using a pre-built module. A friend suggested building one from discrete components — I'm studying buck converters in class right now, so this is a natural extension of what I'm already learning.
