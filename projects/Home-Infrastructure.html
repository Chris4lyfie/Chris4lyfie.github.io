Systems / Network Engineering
2025 – Present

Trust boundary design, service isolation, and recovery-path engineering across network, compute, and storage layers.

Confidentiality: Internal IPs, credentials, and device-identifying labels are omitted. This entry focuses on architecture decisions, failure modes, and how the system evolved over time.
Why I Built This
It started with Plex
  • Wanted to stream movies from a hard drive to any device at home — that was the whole idea.
Then came automation
  • Automating the media stack meant software phoning out to the internet, which meant actually thinking about what was exposed.
That led to segmentation
  • One firewall question led to VLANs, which led to a full network redesign I did not plan on doing.
Then the scope grew
  • Added a server, started experimenting with virtualization and Docker — at some point it stopped being about movies.
System Goal

Build a platform that could host services and isolate risk without making the network a pain to manage or recover from. The design priority is clear trust boundaries and a preserved recovery path — not maximum features.

One router, one managed switch, a small set of physical hosts. Complexity is a risk surface — every extra trunk link is another place a misconfiguration can lock you out. The architecture is a direct response to learning that the hard way.

Network Topology
Current Architecture
L3 / Policy
  • TP-Link ER605v2
  • Terminates all 5 VLANs
  • Enforces all inter-VLAN firewall rules
  • Single routing and policy control point
L2 / Distribution
  • Netgear GS308E v4
  • Single managed switch
  • Carries all VLANs to wired endpoints
  • Cat6 trunk to router in a separate room
Wireless
  • TP-Link EAP660 HD
  • SSID-to-VLAN mapping
  • Serves Management, Home, IoT, Guest SSIDs
  • Multi-VLAN trunk directly to the router
Compute / Services
  • TrueNAS — storage and all app workloads
  • Raspberry Pi 3 — Pi-hole DNS
  • Raspberry Pi 3 B+ — Nginx Proxy Manager
  • Proxmox host — powered down to save power

Keeping L3 policy at the router and L2 behavior at the switch creates a clear fault boundary: routing and firewalling problems are router problems; connectivity problems are switch problems. Mixing these responsibilities makes failures harder to isolate.

Network Segmentation Model

VLANs enforce trust boundaries, not just network organization. Cross-VLAN access is explicit and allowlisted. Nothing is implicitly reachable from another zone.

VLAN Name Purpose Trust Level
10 Management Infrastructure devices, core services, admin plane Highest
15 Home Personal devices — semi-trusted, no management access Medium
30 IoT Untrusted devices — constrained by default Low
40 DMZ Isolated experiments and lab workloads — blast-radius containment Untrusted
50 Guest Guest Wi-Fi — internet only, no internal access Untrusted

Non-negotiable rule: No non-management zone can initiate access into VLAN 10. Management may initiate access outward for administrative purposes. The reverse is never permitted.

Inter-Zone Policy
Source Zone Destination Policy Notes
Management All zones ALLOW Administrative control plane only
Home Management DENY Personal devices have no management access
Home TrueNAS / Plex LIMITED Media access only — explicit allowlist entry
IoT Management DENY Untrusted devices blocked from all internal access
IoT Plex / Media DENY Media access restricted to Home zone only
Guest Internal zones DENY Internet egress only

All zones Pi-hole (DNS) DNS ONLY DNS explicitly allowlisted; all other cross-VLAN traffic to VLAN 10 denied
Service Platform

Infrastructure services and application workloads live on separate hardware. DNS and the reverse proxy each run on their own low-power device, and every app runs on the TrueNAS host. A heavy workload or a storage problem can take apps down, but it can't take the network's name resolution or routing with it.

TrueNAS — Primary Host
  • Plex media server
  • Automated arr stack (Sonarr, Radarr, Prowlarr)
  • qBittorrent behind Gluetun with a VPN kill switch
  • Gitea + PostgreSQL — private Git server
  • Minecraft server, Tailscale remote access
Pi-hole — DNS
  • Dedicated Raspberry Pi 3 v1.2
  • Resides on VLAN 10 (Management)
  • Serves all zones via explicit firewall rules
  • Local .home hostnames point at the reverse proxy
Nginx Proxy Manager
  • Raspberry Pi 3 B+
  • Reverse proxy for internal services
  • Decouples service URLs from device IPs
  • Staged for potential future TLS termination
Prometheus — Proxmox Host (Parked)
  • Supermicro board, Xeon D-2141I, 256 GB ECC
  • Ran Ubuntu and Debian VMs, including a DMZ game server
  • Powered down; workloads moved to TrueNAS
  • IPMI stays reachable for remote power-on

Pi-hole is kept on a dedicated low-power device because DNS is infrastructure-critical — if it fails, all zones lose internet resolution with no automatic fallback. Keeping it independent means a TrueNAS restart or storage event doesn't take DNS down with it. This is an intentional fail-closed design: there is no silent bypass to a public resolver.

Every internal service gets a readable hostname. Pi-hole answers every .home name with the reverse proxy's address, and the proxy forwards each one to the right host and port. Services can move between hosts without anyone's bookmarks breaking.

Compute Consolidation Decision
Architecture Decision Record — Park the Hypervisor, Consolidate on TrueNAS

Context: The lab ran two always-on servers: the TrueNAS storage host and a dedicated Proxmox hypervisor. Proxmox hosted a Docker VM and a game server, but none of these workloads needed a second machine. TrueNAS was already running the media stack, with spare CPU and RAM.

Decision: Move every workload onto TrueNAS as native apps or Docker Compose stacks and power the hypervisor down. The cost of running both machines 24/7 wasn't justified by what the second one was doing.

  • Lower power bill — one always-on server instead of two
  • One app platform — every service is managed, updated, and backed up the same way
  • Hardware stays ready — Proxmox is installed and IPMI is reachable, so it can be powered on remotely when a workload needs it

Tradeoff accepted: TrueNAS is now a single point of failure for every app. That's acceptable because the critical network services — DNS, the reverse proxy, and routing — run on separate hardware, and the app data is snapshotted and replicated (see below).

Storage & Data Protection

Storage on TrueNAS is split by what the data is and how bad it would be to lose it. Small, valuable data sits on mirrored SSDs. Bulk media sits on a large single drive that can be rebuilt if it's lost.

Pool Layout Holds Protection
App data 2 × 512 GB SSD mirror Config and databases for every app Survives one drive failure; snapshotted and replicated nightly
Backup A 8 TB HDD Replicated copy of the app data pool Nightly ZFS replication
Backup B 8 TB HDD Second replicated copy of the app data pool Nightly ZFS replication; scrubbed weekly
Media 14 TB HDD Media library and downloads Short-retention snapshots — replaceable data
Snapshots by Change Rate
  • Whole app pool: daily, kept 3 days
  • Game server and arr configs: hourly for a day, plus dailies
  • Media: daily, kept 2 days
  • Download client excluded by design
Integrity Checks
  • Monthly scrub on every pool
  • SMART short tests three times a week
  • SMART long test monthly, the day after scrubs
  • Scrubs and long tests run on separate days
Isolation
  • Containers run as a dedicated service user
  • App data (API keys, credentials) is never shared over SMB
  • Only the media library is exposed on the network
  • Torrent traffic can only leave through the VPN

The known gap is offsite backup. Both replicated copies live in the same machine as the original, so a fire or power surge could take out all three. That's the next storage item to fix.

Recovery Path

Both the router and the switch keep one port reserved for management access that is never touched during changes. If a trunk or VLAN change goes wrong, there is always a known-good cable to plug into. A spare switch is also kept on hand for an emergency flat-network rebuild.

Architectural Simplification Decision
Architecture Decision Record — Collapse to Single Switching Layer

Context: The original design used multiple managed switches with split responsibilities. Each additional switch introduced more trunk links, more VLAN tagging decision points, and more places where a single misconfiguration could eliminate the management path entirely.

Decision: Collapse to a single core switch. One trunk to the router. Minimal tagging surfaces. All wired connectivity through one documented device.

  • Fewer devices — fewer failure domains to manage simultaneously
  • Fewer trunks — fewer places a VLAN misconfiguration can cause a full lockout
  • Reduced configuration drift — one switch config to maintain, not two or three
  • Clear fault isolation — if switching is broken, there is one place to look

Tradeoff accepted: The single switch is now a single point of failure for all wired connectivity. A spare switch is staged for emergency flat-network recovery, and the router retains a fallback untagged management port.

Intentional Tradeoff
Accepted Tradeoff
Single Core Switch — Simplicity Over Redundancy
A redundant switch topology would eliminate the single point of failure at the switching layer. It would also reintroduce the exact multi-switch trunk complexity that caused the management lockout incidents documented below. The decision to accept switch-level failure risk in exchange for dramatically reduced configuration surface area is deliberate. Recovery from a failed switch — swap hardware, restore config — is faster and more predictable than recovery from a management lockout caused by a trunk misconfiguration on a live, multi-switch system.
Incidents as Design Evidence

These failures weren't random. Each one identified a place where the architecture needed a hard guardrail. The permanent changes they produced are what make the current design defensible.

Incident 1 — AP Firmware Reset Broke Management Access · July 2025 · ~60 min
Failure ModeFirmware update silently reset management VLAN configuration on the access point
SymptomAP became unreachable on the management VLAN immediately after the update completed
RecoveryDirect-wired laptop with static IP in the management subnet → manually reconfigured VLAN settings
Root CauseFirmware updates were not treated as change events requiring post-update verification
Permanent ChangeFirmware updates are now change events: management VLAN verification is a required step before considering the update complete
The core lesson: firmware updates are not safe operations. They can reset configuration silently. Without a direct-connect recovery path, this would have required a full factory reset and rebuild from scratch.
Incident 2 — Cross-VLAN DNS Failure · July–Sept 2025
Failure ModeDevices on non-management VLANs lost internet access after being pointed at Pi-hole for DNS
SymptomRouting and NAT were functional; DNS resolution failed silently with no error surfaced to users
Root CauseRouter firewall did not permit cross-VLAN DNS traffic to VLAN 10 by default
RecoveryValidated routing independently, isolated DNS as the sole failing component, added explicit per-VLAN firewall rules allowing DNS only
Permanent Change"DNS is a controlled shared service" rule: explicit allowlist for DNS traffic only; all other cross-VLAN access to VLAN 10 denied by default
This established the principle that shared infrastructure services must be explicitly allowlisted — never assumed reachable. DNS is now treated as a first-class dependency, not an ambient background service.
Incident 3 — Trunk Misconfiguration Caused Full Management Lockout · Aug 2025 · ~60 min
Failure ModeChanged tagged/untagged VLAN settings across multiple switch ports simultaneously, eliminating the management path
SymptomComplete loss of access to both the switch and the access point
Root CauseNo dedicated management-only port existed; all ports were within the change scope
RecoveryFactory reset → incremental VLAN rebuild → management access restored before re-introducing trunk configuration
Permanent ChangeDedicated management-only port on both router and switch; VLAN changes one port at a time; physical port-to-VLAN map maintained
This incident directly motivated the single-switch consolidation. Multi-switch topologies multiply the number of places this class of mistake can occur. Reducing to one switch with one documented port map was the architectural response.
Incident 4 — Storage Mirror Ran Degraded for Two Months · Aug–Oct 2026
Failure ModeAn SSD in the app-data mirror logged a burst of 35 uncorrectable read errors. ZFS faulted it and the pool kept running on the remaining drive.
SymptomNone. Every app kept working, so nothing prompted a check.
DetectionThe first run of a new monitoring check flagged the degraded pool, roughly two months after the fault.
DiagnosisIt was the second SSD to fail in the same drive bay. Reseating power brought it back, but a scrub found new read and checksum errors right away. SATA CRC errors stayed at zero, which pointed at power to that bay rather than the data cable.
RecoveryInstalled a new SSD in a different bay with a new SATA cable, a different port, and direct PSU power. The resilver copied 75.6 GiB in 5.5 minutes with zero errors.
Permanent ChangePool and disk health are now checked every minute, with alerts sent to me as Discord messages. The old bay is retired. The other mirror SSD is the same model and age, so it's scheduled for replacement with a different brand.
A mirror only protects you if you know when one side has failed. For two months the pool was one drive failure away from losing every app's data, and nothing looked wrong. Redundancy without monitoring just delays when you find out.
Incident 5 — Locked Out of the DNS Host · Oct 2026
Failure ModeLost the login credentials for the Raspberry Pi running Pi-hole
ConstraintRe-imaging would wipe the DNS settings, blocklists, and local hostname records the rest of the network depends on
RecoveryPulled the SD card and added a one-shot script to the boot partition, launched through the kernel command line. On the next boot it reset the password, enabled SSH, restored the original boot line, and deleted itself. The Pi came back with its config untouched.
SnagsWindows hid a .txt extension on the script, Windows line endings broke bash, and the boot command line had to stay a single line with no trailing newline
Follow-UpUpdated Pi-hole and the OS, then traced a separate .home lookup failure on my laptop to the VPN client claiming all DNS queries. Pi-hole itself was fine.
Permanent ChangeThe whole procedure is written up as a runbook. Key-based SSH login is next, so a password is no longer the only way in.
While the Pi was off, every device that relies on it lost name resolution. That's why the recovery had to be fast and non-destructive: rebuilding DNS from scratch would have turned a forgotten password into an outage for the whole network.

How I Would Scale This

The single switch was the right call for this environment, but at larger scale I'd add a second one — the redundancy is worth the added complexity when other people are depending on the network staying up. The segmentation model and the single L3 policy point would stay the same; that part scales fine.

The first thing I'd add in a real work environment is full monitoring and alerting. I've started on that at home: storage and app health are now watched around the clock (see below). Incident 4 is why — a degraded mirror went unnoticed for two months. The network gear still isn't monitored, so a failure there is only found when someone notices. Beyond that, the change discipline I follow in my head — change one thing at a time, verify before moving on — would need to become actual documentation and automated checks. You can't rely on everyone just knowing the rules.

In Progress — Ink

Ink is a personal assistant I'm building on top of the lab, and it's becoming the lab's monitoring layer. It runs as a Discord bot in a custom app on TrueNAS, with a small CPU-only embedding model alongside it for long-term memory. For chat it uses a larger language model on my desktop's RTX 4090. The desktop sleeps when idle, so Ink wakes it with Wake-on-LAN when it's needed, and it shuts itself down again about ten minutes after the last reply.

Next Engineering Improvements

These are committed next steps, not aspirational items.

01
Encrypted Configuration Backups

Export and store router, switch, and AP configs after every baseline change. Currently, recovery from a failed device requires a rebuild from memory — slower and error-prone. Versioned config backups reduce recovery time and eliminate configuration drift after hardware replacement.

02
Formalized Post-Change Verification Checklist

The three network incidents above could have been detected faster with a structured post-change verification pass. The checklist will cover: management VLAN reachability, DNS resolution from each zone, inter-VLAN deny rules, and wireless SSID-to-VLAN mapping. Firmware updates are included as change events requiring the full checklist.

03
Decouple Remote Access from TrueNAS

The Tailscale overlay node currently runs on TrueNAS. A TrueNAS restart or storage event removes remote access entirely. Moving the overlay node to a lightweight independent host — a dedicated Pi or the Nginx device — creates a separate failure domain for remote access and removes the hard dependency on the primary storage host.

04
Offsite Backup

App data is replicated to two other pools every night, but all three copies sit in the same machine. An offsite or cloud copy of the app data would protect against losing the whole server to a fire, theft, or power surge.
